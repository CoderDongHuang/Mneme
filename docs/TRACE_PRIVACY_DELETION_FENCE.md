# Trace 与隐私策略的账号删除围栏

对应原审查 P1-05 / MN-006 的跨存储删除、异常传播、独立残留检查与重试要求。本项仅处理 Trace 和隐私策略；知识索引和反思已有独立协议，长期记忆、会话及缓存迟到写入仍需各自验收，不把整个删除 Saga 提前标记完成。

## 行为与边界

复用已有持久用户 generation 行。Trace 插入和隐私策略保存只在实际存储阶段持有该用户数据库锁；账号删除先永久 tombstone，再清理。已进入锁的写入先结束，删除后才到达的写入被拒绝。数据库读取失败直接失败，不降级为允许处理。已删除用户即使策略行已移除，也不能恢复默认云授权；外部模型授权检查保留 StaleGeneration 契约。

删除提交后独立 COUNT；静默 DELETE 或 COUNT 故障向上抛出，让删除任务保持可重试。普通“删除我的 Trace”不删除账号、不设置 tombstone，之后正常交互仍可记录新 Trace。账号 tombstone 保留，不因清理策略行或重启而消失。

不能撤回已经发送给模型供应商的请求，不在供应商调用期间持数据库锁。SQLite 为单主机模式；多实例须使用既有共享 MySQL 配置。这里保证逻辑不可复活与可验证清理，不承诺备份、WAL 或底层介质物理擦除。没有新增依赖、配置或迁移。

## 验证

全量 Python 3.11 Ruff 和 867 项测试通过；新增与原隐私定向 12 项通过，覆盖新实例、并发写入、另一用户隔离、静默删除、读取失败和恢复重试。真实部署内独立脚本在 SQLite、MySQL 各执行一次存储并发、tombstone 持久、迟到拒绝、零残留和另一用户不受影响。独立脚本仅在自己的进程延迟存储调用，不修改服务进程；保留前缀的合成身份最终清理，不能移除正式账号 tombstone。

实际 localhost 桌面、手机四项回归通过，无整项重试：真实注册隔离账号，使用应用实际配置的 SQLite，核对并发删除和另一用户网页策略刷新；原隐私页保存、审计 GET 故障、重试和手动清 Trace 保持。最后通过正式删除 API 提交任务，等待持久 tombstone 和零残留后再用新进程尝试迟到写入。接受回执不能代替后台删除完成。仅原隐私页只读 GET 故障使用浏览器夹具，不模拟删除结果。

十张安全截图逐一复核，无横向溢出。独立读回测试账号零、261 个删除任务全 completed；212 个持久已删除用户的 Trace/策略残留均零，合成 manifest 行零，三个部署文件哈希一致，Gateway/Agent 均健康。失败的 MySQL 环境假设和未等待后台完成记录保留；修正测试生命周期后完整重跑。真实页面和双存储验收均加入整栈 CI。

部署前停全部应用写入者，保留 SQL、旧容器及配置。锁文件未变，本地验收镜像基于锁哈希一致的已验收镜像复制源码；正式 CI 使用标准全量 Docker 构建。回退须停止所有新工作器，恢复匹配镜像和数据点；旧代码不理解围栏，不支持混跑。证据索引见整改记录。
