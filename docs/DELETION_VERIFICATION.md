# 文档、知识库与账号删除核验

删除接口提交后台任务。只有外部存储独立读回为零，且同一有效 owner/fence 的事务删除 MySQL 记录并再次读回为零，任务才能完成。调用成功本身不作为无残留的证据。

## 核验范围

| 存储 | 文档 | 知识库 |
| --- | --- | --- |
| Qdrant | 所有已配置分片中匹配用户、知识库及文档的片段 | 匹配用户和知识库的片段及集合 |
| FTS5 | 用户、知识库及文档行数 | 用户和知识库行数 |
| 文件与缓存 | 当前版本、全部历史版本及对应对象缓存 | 全部版本、对应缓存、本地知识库目录 |
| 对象存储 | 版本对象逐个 stat | 逐个 stat 及知识库前缀递归 list |
| MySQL | 文档、版本、标签 | 知识库以及原始文档清单对应的文档、版本、标签 |

旧命名集合和旧 Embedding profile 不阻止清理；分片配置必须包含所有仍持有数据的分片。已下线且未配置的存储不能被在线程序核验。

`processing_task.cleanup_report` 保存检查时间和数量，不保存正文、密钥或文件路径。数值 `-1` 表示读取失败，绝不能当作零。对象存储仅明确的 NoSuchKey 当作不存在，网络和鉴权错误保持未知。MySQL 的文档和版本清单保留到外部存储核验通过，支持在远端对象已不存在、缓存仍残留时重试。

## 故障处理

任务中心选择文档删除或资料库删除任务，展开“清理核验”查看残留；管理员运维的删除任务表也提供相同清单。修复权限、存储或网络故障后，使用任务中心的“重试任务”。自动尝试耗尽后保留失败状态和历史阶段记录，不能通过手工改 completed 绕过核验。

### 维护限流退避

Gateway 后台任务收到 Agent 的 HTTP 429 时，将 `retry` 和下一次执行时间写入数据库，并释放执行租约；不占用线程等待，也不消耗存储故障的重试次数。识别原异常因果链中的 429，接受 `Retry-After` 秒数或 HTTP 日期，缺失/非法时默认 60 秒，等待限制在 30 秒至 24 小时之间。Gateway 重启后由原任务继续执行，无需重新提交删除。持续限流时任务保持等待，不会冒充完成；应排查维护流量和部署容量。账号删除 Saga 使用同一退避规则。

核验读取受限仍保存 `-1` 和 `pending`。只有受限读取导致未知时才使用上述等待规则；其他存储读取失败、实际非零残留及普通异常继续使用原有有限重试。限流错误只记录固定提示，不将上游响应正文写入任务、阶段日志或服务日志。限流分桶、服务鉴权、owner/fence 以及完成前清零核验均保留。

`cleanup-backoff-real.spec.js` 使用只读探针共享 Gateway 网络命名空间，真实耗尽 Agent 维护预算；桌面和手机检查任务等待、次数不变、SQL 清单保留、租约释放，随后重启 Gateway 并核对两种删除任务自动完成及清理报告全零。测试仅在 `MNEME_REAL_E2E=true` 且 `MNEME_RATE_LIMIT_QA=true` 的隔离环境启用，按串行执行。

V28 是增加 JSON 列的兼容迁移。升级前备份数据库并停止旧 worker，再部署所有 Gateway 与 Agent。回滚程序前保留任务和版本清单，不得删除尚未核验的数据；不理解核验协议的旧 worker 不应接管这些任务。

## 保证边界

本清单核验在线存储的逻辑删除；SQLite 的 WAL、空闲页、Qdrant 底层文件、对象历史版本、备份、快照和存储介质不能由零行数证明物理不可恢复。物理擦除需要单独的留存、维护及介质策略，不能在共享数据库在线运行期间直接删除 WAL 文件或擅自清除其他用户的备份。

账号最终清单覆盖下述在线资源；它仍不能证明备份、WAL 或底层介质已经物理擦除。下述离线维护仅回收当前 SQLite 文件的空间；P2-12 的其他存储、留存策略和容量治理单独验收。

## SQLite 停写维护

删除请求只负责逻辑清理与独立读回，不在 HTTP 请求中执行全库 VACUUM。维护需安排停机窗口，覆盖所有 Gateway、Agent 副本及其他直接访问同一数据目录的进程。不要直接删除 `-wal`、`-shm` 或主数据库文件，也不要用旧备份覆盖在线目录。

1. 先按 [自托管指南](SELF_HOSTING.md) 生成并核验一组匹配的恢复资料；确认备份可读取、目标磁盘有至少两倍 SQLite 主库大小加 1 MiB 的可用空间。只保留符合部署方留存策略的必要恢复组。
2. 在仓库根目录运行 `python scripts/maintain_sqlite.py --container mneme-python-agent-1` 查看计划。脚本从实际容器配置和挂载发现路径；不读取宿主机猜测路径，不向输出写入凭证或正文。
3. 记录并停止全部 Gateway 与 Agent 副本，停止其他直接写入同一挂载的进程。保留容器和挂载供离线维护使用；MySQL、Redis 与 Qdrant 可继续运行。脚本不会自动停启服务。
4. 执行 `python scripts/maintain_sqlite.py --container mneme-python-agent-1 --apply`。若仍有相关服务或持有同一数据挂载的容器运行，脚本拒绝执行。通过后使用该 Agent 的实际镜像与数据挂载启动无网络、只读根文件系统的短期维护容器；只传递目标路径，不传服务凭证。目标镜像必须包含 `app.storage.sqlite_maintenance`。
5. 检查整体 `status=completed`，每个库 `logical_data_unchanged=true`、`after_bytes.-wal=0`。工作进程核验独占锁、空间、SQLite 完整性及逻辑快照，执行 FTS optimize、VACUUM 和 TRUNCATE checkpoint，再核验空闲页及 WAL。缺库、只读、忙锁、损坏和空间不足均为失败，不创建空库替代；部分成功仍整体失败，修复原因后可以重试。
6. 恢复原有服务与副本，等待 Agent `/health/ready` 和 Gateway 就绪，再用存活账号检查知识库列表、文档状态和检索。保留简短维护回执，清理临时测试账号；无需保存正文快照或大量截图。

SQLite 辅助后端维护词法索引、generation、记忆版本、Trace 和隐私五个库；`AUXILIARY_STORE_BACKEND=mysql` 时只维护词法索引，不能据此声称 MySQL 已压缩。generation 的永久账号删除围栏保留，防止旧任务重新写回。物理空间回收不会删除仍受留存策略约束的有效记录。

维护失败时保留原数据目录和完整错误状态，不手工改成功回执。检查权限、挂载、外部进程与空间后重试；怀疑损坏则维持停写并使用经核验的匹配恢复组，按恢复流程同时恢复相关存储和删除围栏，再重新核验删除清单后开流量。不要恢复一个过时 SQLite 文件并继续使用新版本的其他存储。

此操作仅证明当前 SQLite 数据逻辑未变且 WAL/空闲页已回收，不能证明文件系统旧块、SSD、快照、备份、Qdrant 底层文件或对象历史版本不可恢复。历史恢复组按部署方的到期策略清理；如要求不可恢复擦除，需结合介质加密、密钥销毁及存储供应方流程。恢复旧备份可能重新引入已删数据，必须重放删除记录和永久围栏后再开放服务。

维护测试覆盖真实崩溃遗留 WAL、FTS 删除段、其他租户及永久围栏、读写忙锁、缺库/损坏/越界/符号链接、空间不足和部分失败重试；真实 localhost 桌面、手机分别停止全部写入服务、比较五库逻辑快照、执行维护、恢复就绪并检查存活文档，最后读取测试账号 18 项清零报告。

## 账号文件与 SQL 清单

AccountFileCleanup 从当前文档和全部历史版本分别按主键分页（每批 256）读取位置。先按清单删除文件/对象与缓存，再清用户对象前缀和本地用户目录；随后重新读取清单逐位置检查，并独立核验前缀和目录。仅靠远端前缀无法发现“远端已缺失、缓存仍在”的对象，因此 SQL 清单必须保留到全部核验成功。空位置、读取失败和非零残留均阻断删除，不将异常当作零。

Saga 在 file_cleanup 和 user_delete 前均执行幂等文件清理及核验，恢复旧检查点也不能绕过；头像删除后检查路径，无法取得用户快照时头像计数为未知，不能凭缺失快照证明无残留。目录遍历使用 walkFileTree，有界保留路径，拒绝越界及符号链接路径。此处不承诺对象历史版本、WAL、快照或介质物理擦除。

## 账号最终汇总

V34 新增 `account_deletion_task.cleanup_report`。管理员运维页的“账号删除 Saga”可展开“清理核验”，查看以下 18 项。Agent 内部 GET `/api/v1/admin/user/{user_id}/deletion-report` 受服务鉴权保护，直接读取存储，不使用会隐藏过期数据的 UI 列表。

| 来源 | 计数 |
| --- | --- |
| Qdrant / SQLite 索引 | 向量片段、向量集合、词法索引行 |
| 账号状态 | 写入围栏缺失数（已建立永久删除围栏时为零） |
| 记忆及辅助数据 | 长期记忆、记忆版本、执行记录、隐私设置、工具授权与用量 |
| 会话 / Redis | 原始会话清单、用户前缀缓存、反思计数与租约、反思队列任务 |
| 文件 | 当前及历史文件与缓存、对象前缀、本地目录、头像 |
| MySQL | 用户及 21 张直接归属表的记录总数，关联子表由外键级联删除 |

任何负数、缺项、错误类型或读取异常都不能视为零。进入最终 SQL 删除前重放各阶段清理，外部计数必须全零；用户删除、独立 SQL 读回、报告保存、阶段日志和任务完成在同一 owner/fence 事务内提交。SQL 计数失败会回滚，保留用户及版本清单；外部清理是幂等的，修复后可重试。工具授权和配额写入也受账号围栏保护，避免删除后在途写入复活记录。

审计日志、操作回执、删除任务和永久删除围栏有独立留存目的，不计入业务清零。历史任务若已经丢失用户快照，必须先恢复核验所需清单，不能手工将未知改为零。上线前停止旧 worker，完成 V34 并同时部署理解新协议的 Gateway 和 Agent；旧 worker 不得接管这些未完成任务。

AccountFileCleanupTest 使用真实 MySQL/Flyway、S3 服务和文件系统，覆盖已缺失对象的当前/历史缓存、另一租户、读回残留/异常、旧检查点、SQL 静默未删、两类清单分页。account-files-real.spec.js 在真实 localhost 的新租户建立两个版本，将该历史清单位置改为空制造故障：通过隐私页提交删除，确认任务重试且 SQL 依据保留。恢复清单后，在该账号的隐私表上注入限定用户的静默删除故障，确认原始计数为 1、任务仍可重试；解除故障后 18 项全零。专用 QA 管理员通过真实角色及凭证验证，在运维页展开失败和成功清单；另一账号文件哈希和知识库页面保持正常。finally 移除触发器并正常删除所有 QA 账号。夹具不模拟 HTTP 成功，也不冒充生产存储整体故障。

## 验收

Python 使用真实 Qdrant 本地存储和 SQLite，注入静默不删除及读取失败。Java 使用真实 MySQL/Flyway、事务及 MinIO，覆盖历史版本、缓存残留、鉴权失败、错误回执和 SQL 删除回滚。整栈 Playwright 在专用新租户的 SQLite shadow 表上注入限定用户的 DELETE 故障，桌面和移动端分别验证失败清单、界面重试、最终零计数及其他租户隔离，finally 移除触发器并提交测试账号删除。
