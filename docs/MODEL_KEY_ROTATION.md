# 用户模型配置密钥迁移与轮换

模型配置使用独立的 AES-GCM 密钥。生产 Compose 设置 `MNEME_PRODUCTION=true`，缺失 MODEL_CONFIG_ENCRYPTION_KEY、短于 32 字符、或与 JWT_SECRET 相同时拒绝启动。独立密钥下更换 JWT_SECRET 不影响模型配置。非生产保留 JWT 回退以兼容本地部署，运维页明确提示；仍建议独立配置。

## 升级已有部署

1. 维护窗口内暂停模型设置写入，备份数据库及部署配置，在密钥管理器中保留原密钥；多实例必须同时使用同一版本和密钥环。
2. V25 迁移只给旧行补充 `key_version=legacy-v1`，保留原密文。把原 MODEL_CONFIG_ENCRYPTION_KEY（原先为空则为当时 JWT_SECRET）放入密钥管理器的 MODEL_CONFIG_PREVIOUS_KEYS：JSON 对象以 `legacy-v1` 为键、原密钥为值。不要把真实 JSON 放入 shell 历史、代码仓库或备份归档。
3. 配置新的独立 MODEL_CONFIG_ENCRYPTION_KEY，MODEL_CONFIG_KEY_VERSION 使用全新版本（默认 v2），保留旧密钥环。不得将同一版本名绑定不同密钥。所有实例更新后确认运维页列出历史版本及“需要轮换”，无 missing_keys。
4. 运行 `python scripts/rotate_model_keys.py --url https://你的域名 --username 管理员账户 --expected-version v2` 检查状态。脚本交互输入密码和管理员凭证，不打印密钥；仅 HTTPS 或本机 HTTP，拒绝重定向。确认版本后加 `--apply` 执行。
5. 服务在单一事务中锁定各行，按原版本解密、用新密钥加密、逐条解密校验，然后提交。任意错误全部回滚，原密文保留；不返回空配置，不允许用“清除密钥”覆盖无法解密的旧行。重复执行只校验，不重复迁移。
6. 返回 verified 应为所有配置行数，rotated 为实际迁移数；运维状态变为 current。实际账户打开设置并执行供应商连接测试。Beta 使用全表事务，数据量大时应预留维护窗口和数据库锁等待时间，超时后先检查状态再重试。

后续 v2→v3 使用相同步骤，将 v2 加入旧密钥环、配置新的 v3 当前密钥。管理员接口 `/api/v1/admin/model-keys/rotate` 同时要求有效会话与 X-Admin-Token。

## 失败与恢复

缺密钥或 GCM 校验失败时恢复原版本的真实密钥，不要更换版本名蒙混通过。错误不会携带明文密钥、用户配置或底层解密原因。密钥丢失无法通过技术手段恢复，必须从独立保管的密钥管理器取回。

整站备份 metadata.model_config_keys.required_versions 记录数据库使用的版本列表，不含密钥。恢复工具在停服前检查实际 Compose 配置：缺少版本、无效密钥环或生产复用 JWT 时拒绝恢复。V21–V24 旧备份无版本信息，按 legacy-v1 检查；更早无模型配置的备份不需要该密钥。版本存在不代表密钥内容正确，恢复后必须验证模型读取；错误时使用恢复前快照和对应密钥回滚，不重新保存覆盖。备份加密的 BACKUP_KEY_VERSION 与模型配置密钥版本独立。

即使当前数据库已全部迁移，仍需保留所有未过留存期备份所需的旧密钥。只有相关旧备份全部到期并验证新备份恢复成功后，才能从在线密钥环移除旧版本；历史密钥按独立安全保管策略保留。V25 为增加字段的兼容迁移，旧程序无法读取新版密文，回滚程序版本必须同时恢复对应数据库快照和原密钥，不得只回滚镜像。
